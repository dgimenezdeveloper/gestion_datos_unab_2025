# **Entidad vs Atributo (definiciones operativas)**

Modelo: Relacional · Tecnología: MySQL 8.x · Herramienta: MySQL Workbench

**Notación U·S·C:** U \= Unidad, S \= Semana, C \= Micro‑concepto. Ejemplo: *U1·S1·C5* indica “Unidad 1, Semana 1, Micro 5”.

## **Qué resuelve este micro**

Establece pruebas rápidas para decidir si algo del negocio debe modelarse como **entidad** o como **atributo**. En la U1 trabajamos con una sola entidad (*Cliente*) y confirmamos que *teléfono* es un **atributo multivaluado** (no una entidad aparte en el nivel conceptual).

## **Definiciones operativas**

| Término | Definición operativa | Prueba rápida |
| :---- | :---- | :---- |
| **Entidad** | Objeto del negocio que *existe por sí mismo* y del que necesitamos conservar *múltiples registros* con identidad propia. | ¿Se puede identificar de forma única y *recibir eventos* (altas, cambios)? |
| **Atributo** | Propiedad que *describe* a una entidad. | ¿Depende de una sola entidad y no tiene vida independiente? |
| **Atributo multivaluado** | Propiedad que puede tener *0..n valores* por entidad. | ¿Pueden existir varios valores del mismo tipo para el mismo cliente? |

## **Árbol de decisión en 5 preguntas**

| Pregunta | Sí → | No → |
| :---- | :---- | :---- |
| ¿Tiene identidad propia en el negocio? | Posible **entidad**. | Probable **atributo**. |
| ¿Recibe eventos o cambios a lo largo del tiempo? | Refuerza que sea entidad. | Atributo. |
| ¿Se relaciona con varias otras cosas del negocio? | Probable entidad (en U2/U3 se verá). | Atributo. |
| ¿Su existencia depende totalmente de otra entidad? | Podría ser *atributo* o *entidad débil* (tema de U2). | Entidad independiente. |
| ¿Puede tener múltiples valores del mismo tipo por cada entidad? | **Atributo multivaluado** (en el lógico se materializa con una tabla aparte). | Atributo simple. |

## **Ejemplos del caso “Tienda de Ventas” (U1)**

| Expresión (lenguaje natural) | ¿Entidad o atributo en U1? | Justificación |
| :---- | :---- | :---- |
| Cliente | **Entidad** (única en U1) | Existe por sí mismo y lo identificamos con `id_cliente`. |
| Teléfono | **Atributo multivaluado** | Describe a Cliente; puede haber 0..n valores. En el lógico será una tabla aparte. |
| Tipo de teléfono (móvil/fijo) | Atributo de “teléfono” | Metadato del número; no tiene vida independiente. |
| Correo electrónico | Atributo | Otro medio de contacto; puede ser opcional. |
| Documento | Atributo | Ayuda a evitar duplicados (R4). |
| Cajero | Actor del SI (no entidad en U1) | No registramos ventas en U1; fuera de alcance. |
| Venta | Entidad (pero *fuera de alcance* en U1) | Se abordará en unidades posteriores. |

## **Tabla de contrastes**

| Términos | Definición operativa | Prueba rápida |
| :---- | :---- | :---- |
| **Entidad** vs **Atributo** | La entidad representa un objeto completo; el atributo describe una propiedad de ese objeto. | ¿Sobrevive sin la otra? Si sí, entidad; si no, atributo. |
| **Atributo simple** vs **multivaluado** | Simple: a lo sumo 1 valor por entidad. Multivaluado: 0..n valores. | ¿Podemos tener más de un valor del mismo tipo para el cliente? |
| **Atributo** vs **Entidad débil** (aviso) | Si requiere identidad parcial y depende de otra entidad para identificarse, podría ser entidad débil. | Tema de U2; en U1 no usamos entidades débiles. |

## **⚠ Atención (errores frecuentes)**

* **Promover actores a entidad** (p. ej., “cajero”) cuando están fuera de alcance.  
* **Telefónos separados por comas** en una sola columna: viola 1FN.  
* **Crear entidad “Teléfono” en el conceptual** solo para que haya dos tablas en el lógico.

## **✔ ¿Qué me llevo?**

* □ Distingo **entidad** de **atributo** con pruebas claras.  
* □ Confirmo que en U1 la única entidad es **Cliente**.  
* □ Decisión: **teléfono** es **atributo multivaluado** (0..n) y no entidad.  
* □ Evito errores típicos que rompen 1FN o inflan el alcance.

## **Trazabilidad Conceptual · Lógica · Física**

| Capa | Impacto en este micro | Qué se implementa más adelante |
| :---- | :---- | :---- |
| **Conceptual (E‑R)** | Fija que el DER de U1 tendrá una **única entidad (Cliente)** y marca *teléfono* como **multivaluado**. | S2: representar multivaluado en el DER sin crear nuevas entidades. |
| **Lógica (Relacional)** | Anticipa el mapeo de multivaluados a una tabla aparte. | S3: tablas `clientes` y `clientes_telefonos` con PK/FK. |

**Decisión de diseño de este micro:** confirmar *Cliente* como única entidad de U1 y *teléfono* como atributo multivaluado.
