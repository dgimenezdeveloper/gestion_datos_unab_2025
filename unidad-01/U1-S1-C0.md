# **Caso guía “Tienda de Ventas” y alcance**

Modelo: Relacional · Tecnología: MySQL 8.x · Herramienta: MySQL Workbench

**Notación U·S·C:** U \= Unidad, S \= Semana, C \= Micro‑concepto. Ejemplo: *U1·S1·C0* indica “Unidad 1, Semana 1, Micro 0”.

## **Cómo usar este micro**

Este material define el caso guía de la cursada y el alcance del primer ciclo de trabajo. Se utiliza para orientar todas las decisiones de diseño de las semanas 1 a 4\. No incluye diagramas ni SQL; su salida son acuerdos claros que evitan retrabajos posteriores.

## **Contexto del cliente (disparador narrativo)**

### **Situación**

Una tienda minorista de artículos para el hogar (“Tienda de Ventas”) necesita centralizar el **registro de clientes** y sus **datos de contacto** para poder comunicarse de forma confiable. Actualmente esa información está dispersa en papeles y planillas.

### **Dolencias**

* No existe un registro único de clientes; hay duplicados y datos inconsistentes.  
* Los **teléfonos** están anotados en distintos lugares; algunos clientes tienen varios y otros ninguno.  
* No se puede responder con certeza: “¿Cómo contactamos a este cliente?”

**Objetivo del primer ciclo:** construir una base sólida para **registrar clientes** y sus **teléfonos (múltiples por cliente)**, y poder consultarlos de forma simple. Daremos la primera “vuelta completa” (análisis → conceptual → lógico/físico → carga → consulta) *con una sola entidad de negocio*.

## **Qué resuelve este micro**

* Define el **problema**, el **alcance** y los **supuestos** iniciales.  
* Identifica **actores** y **eventos** relevantes de negocio.  
* Entrega un listado inicial de **entidades** y **atributos candidatos** (sin diagramar).

## **Cuándo se usa (en el ciclo de diseño)**

Se aplica en la fase de **análisis de requerimientos**, antes del modelado conceptual. Sus acuerdos condicionan la calidad del diagrama E‑R de la Semana 2 y del esquema SQL en la Semana 3\.

## **Ejemplo del caso (acuerdos iniciales)**

### **Alcance del primer ciclo**

* Registrar **clientes** con datos básicos (nombre, documento opcional, correo opcional).  
* Almacenar **uno o más teléfonos** por cliente (móvil/fijo), cada uno con su número y tipo.  
* Permitir consultas básicas de clientes por nombre, documento, teléfono o correo.

### **Fuera de alcance (por ahora)**

* Ventas, pedidos, ítems de venta, precios y productos.  
* Gestión de stock, proveedores y promociones.  
* Histórico de cambios de teléfono o auditoría de contacto.  
* Dirección postal compuesta y georreferenciación.

### **Reglas de negocio mínimas**

* Cada cliente posee un **identificador único** (`id_cliente`) generado por el sistema.  
* Un cliente puede tener **uno o más teléfonos**; el número no se repite para el mismo cliente.  
* Cada teléfono tiene **tipo** (móvil/fijo) y **número** con formato validado.  
* Debe existir al menos un dato de contacto (teléfono o correo) para considerar al cliente “contactable”.

**Entregables de esta semana:** documento de alcance, lista de atributos del cliente y decisión explícita de tratar **teléfono** como **atributo multivaluado** (justificación).

## **Tablas de contraste**

### **Conceptos cercanos**

| Término | Definición operativa | Test rápido |
| :---- | :---- | :---- |
| **Problema** | Dolencia que impide operar o decidir. | ¿Qué duele hoy y por qué? |
| **Requerimiento** | Necesidad funcional verificable. | ¿Podemos comprobar si se cumple? |
| **Regla de negocio** | Condición que debe respetarse siempre. | ¿Se viola si cambian los datos? |
| **Entidad** | Objeto de negocio que queremos registrar. | ¿Tiene identificador propio y atributos? |
| **Atributo** | Propiedad simple de una entidad. | ¿Depende de un solo objeto? |
| **Atributo multivaluado** | Puede tener más de un valor por entidad. | ¿Puede haber 0..n valores para el mismo cliente? |

### **Alcance**

| Incluido | Excluido | Motivo |
| :---- | :---- | :---- |
| Registro de clientes y teléfonos asociados. | Ventas y productos. | Se incorporan en unidades posteriores. |
| Búsqueda de clientes por datos básicos. | Reportes de negocio y estadísticas. | Fuera del objetivo mínimo de la U1. |

## **⚠ Atención (errores frecuentes)**

* **Suponer ventas** en la U1: el foco es *solo* el cliente y su contacto.  
* **Guardar teléfono en una sola columna** con valores separados por comas: viola 1FN.  
* **Duplicar clientes** para “agregar otro teléfono”: genera inconsistencias.

## **✔ ¿Qué me llevo?**

* □ Problema y alcance del primer ciclo definidos *solo para Cliente*.  
* □ Lista de atributos del cliente (nombre, documento, correo, teléfonos...).  
* □ Decisión: **teléfono es multivaluado** (0..n por cliente) y requerirá tabla propia en el modelo lógico.  
* □ Convenciones de nombres acordadas (singular, prefijos, legibilidad).  
* □ Fuera de alcance documentado para evitar crecimiento no planificado.

## **Trazabilidad Conceptual · Lógica · Física**

| Capa | Impacto en este micro | Qué se implementa más adelante |
| :---- | :---- | :---- |
| **Conceptual (E‑R)** | Define **una sola entidad: Cliente** y sus atributos; decide que *teléfono* es **multivaluado**. (El DER mostrará solo la entidad). | Semana 2: dibujar la entidad Cliente en el E‑R, afinando atributos (simples/compuestos). |
| **Lógica (Relacional)** | No se define aún el esquema; se establecen convenciones de nombres. | Semana 3: dos tablas `clientes` y `clientes_telefonos` (por atributo multivaluado), con PK y FK. |
| **Física (SQL)** | No hay código en este micro. | Semanas 3–4: `CREATE TABLE clientes`, `CREATE TABLE clientes_telefonos`, `INSERT` y `SELECT` básicos. |

**Decisión de diseño de este micro:** fijar el *alcance del primer ciclo con una única entidad* (Cliente) y declarar **teléfono** como atributo multivaluado.
