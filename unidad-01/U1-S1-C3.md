# **Requerimientos iniciales y reglas mínimas**

Modelo: Relacional · Tecnología: MySQL 8.x · Herramienta: MySQL Workbench

**Notación U·S·C:** U \= Unidad, S \= Semana, C \= Micro‑concepto. Ejemplo: *U1·S1·C3* indica “Unidad 1, Semana 1, Micro 3”.

## **Qué resuelve este micro**

Convierte la narrativa del cliente en **requerimientos verificables** y **reglas de negocio mínimas** para la primera vuelta de la espiral. Produce una **lista validada de atributos** de la entidad **Cliente** y declara *teléfono* como **atributo multivaluado**.

## **Del problema al requerimiento (formato práctico)**

Usaremos esta plantilla breve para cada necesidad detectada. Un requerimiento debe ser *claro*, *necesario* y *verificable*.

| Campo | Cómo completarlo | Ejemplo (Cliente) |
| :---- | :---- | :---- |
| **Rótulo** | R\# corto y único. | R1 – Contactabilidad |
| **Descripción** | Qué debe poder hacer el sistema (en lenguaje de negocio). | Registrar clientes y asegurar al menos un medio de contacto válido. |
| **Criterio de aceptación** | Qué evidencia mínima demuestra que se cumple. | Dado un alta, el sistema impide guardar si el cliente no tiene teléfono o correo. |
| **Impacto de datos** | Datos nuevos o reglas sobre ellos. | Atributo *teléfono* multivaluado; *correo* opcional; nombre identificable. |

## **Requerimientos iniciales del cliente (ciclo 1\)**

| R\# | Descripción | Criterio de aceptación |
| :---- | :---- | :---- |
| R1 | Registrar **clientes** con datos básicos identificables. | Se puede dar de alta un cliente con nombre y al menos un contacto válido. |
| R2 | Almacenar **0..n teléfonos** por cliente, cada uno con su *tipo* (móvil/fijo) y *número*. | Un cliente puede registrar múltiples teléfonos; no se permite cantidad negativa ni número vacío. |
| R3 | Permitir **búsqueda** de clientes por nombre, documento, teléfono o correo. | Una consulta devuelve el cliente correcto si existe coincidencia exacta o por prefijo en nombre/teléfono. |
| R4 | **Evitar duplicados** evidentes de cliente al momento del alta. | Al ingresar un cliente con mismo documento y nombre, el sistema alerta o bloquea según política. |

**Nota:** R3 y R4 guían validaciones de negocio en U1, y se verificarán con `SELECT` en la Semana 4\.

## **Reglas de negocio mínimas**

| RN\# | Regla | Motivo |
| :---- | :---- | :---- |
| RN1 | Cada cliente posee un **identificador único** (`id_cliente`). | Unívoco para actualizar y consultar sin ambigüedad. |
| RN2 | Un cliente debe tener **≥ 1 medio de contacto válido** (teléfono o correo). | Asegurar contactabilidad mínima. |
| RN3 | Un cliente puede tener **0..n teléfonos**; el **número no se repite** para el mismo cliente. | Evitar redundancia e inconsistencias. |
| RN4 | El **tipo de teléfono** debe ser uno de {móvil, fijo}. | Estandarizar el dominio del dato. |

## **Atributos candidatos de *Cliente* (S1)**

| Atributo | Descripción | Notas |
| :---- | :---- | :---- |
| `id_cliente` | Identificador único interno. | No proviene del negocio; se genera en el sistema. |
| `nombre` | Nombre y/o razón social del cliente. | Suficientemente descriptivo para distinguir. |
| `documento` (opcional) | Identificación fiscal/personal si se dispone. | Usado para evitar duplicados (R4). |
| `correo` (opcional) | Correo electrónico de contacto. | Alternativa al teléfono para RN2. |
| `telefonos[]` (multivaluado) | Lista de teléfonos del cliente. | Cada elemento tendrá *tipo* y *número*. Llevará tabla propia en U1·S3. |

**Convenciones de nombres (S1):** singular para entidades y columnas; prefijos evitados; nombres legibles en español simple.

## **Tabla de contrastes**

| Términos | Definición operativa | Prueba rápida |
| :---- | :---- | :---- |
| **Requerimiento** vs **Regla de negocio** | El requerimiento es una *necesidad*; la regla es una *condición* que siempre se cumple. | ¿Se verifica con un caso puntual (R\#) o se aplica a todos los casos (RN\#)? |
| **Atributo** vs **Metadato** | Atributo \= contenido; Metadato \= regla/forma del contenido. | ¿Se almacena por cliente o describe cómo almacenarlo? |
| **Atributo simple** vs **multivaluado** | Simple: 1 valor por cliente. Multivaluado: 0..n valores por cliente. | ¿Puede repetirse el valor para el mismo cliente? |

## **⚠ Atención (errores frecuentes)**

* Convertir todo en “obligatorio”: algunos datos son opcionales por política (p. ej., documento, correo).  
* Tratar el teléfono como texto libre sin validar dominio (tipo/número).  
* Agregar ventas/productos en U1: está fuera de alcance.

## **✔ ¿Qué me llevo?**

* □ Requerimientos R1–R4 definidos con criterio de aceptación.  
* □ Reglas RN1–RN4 declaradas y comprensibles.  
* □ Lista de **atributos candidatos** para la entidad Cliente.  
* □ Decisión: **teléfono multivaluado** (0..n) y estandarizado por tipo.
