# **De dato a decisión (DIKW) y flujo de información**

Modelo: Relacional · Tecnología: MySQL 8.x · Herramienta: MySQL Workbench

**Notación U·S·C:** U \= Unidad, S \= Semana, C \= Micro‑concepto. Ejemplo: *U1·S1·C1* indica “Unidad 1, Semana 1, Micro 1”.

## **Qué resuelve este micro**

Define por qué necesitamos una base de datos en el caso guía y cuáles **preguntas de negocio** debe responder desde el primer ciclo. Esto evita recolectar datos sin propósito y alinea el diseño con decisiones reales.

## **Qué es y para qué sirve (DIKW)**

**DIKW** resume la transformación desde *dato* (registro crudo) hasta *decisión* (acción informada). Es un marco para justificar qué datos recolectamos y cómo los convertimos en valor.

| Nivel | Definición operativa | Ejemplo en el caso |
| :---- | :---- | :---- |
| **Dato** | Hecho puntual, sin contexto. | “+54 11 5555‑5555” |
| **Información** | Dato con significado para un propósito. | “Teléfono del cliente *N. Gómez*” |
| **Conocimiento** | Patrón/relación que permite inferir. | “Un 30% de clientes tiene más de un teléfono” |
| **Decisión** | Acción basada en la evidencia. | “Solicitar *al menos un contacto válido* para cada alta de cliente” |

## **Cuándo se usa (en el ciclo de diseño)**

Se aplica **antes** de definir atributos. Primero acordamos *qué decisiones* debemos habilitar en la Unidad 1; luego seleccionamos los *datos mínimos* que las soportan. Esto guía el DER de la Semana 2 sin sobredimensionarlo.

## **Flujo de información mínimo (ciclo 1\)**

**Objetivo operativo:** poder *identificar y contactar* a cualquier cliente registrado.

| Pregunta de negocio | Dato mínimo requerido | Dónde vive (U1) |
| :---- | :---- | :---- |
| ¿Cómo contacto a este cliente? | Nombre identificable \+ *≥ 1* medio de contacto (teléfono o correo) | Entidad **Cliente**; teléfono es *multivaluado* |
| ¿Cuántos teléfonos tiene un cliente? | Lista de teléfonos con *tipo* (móvil/fijo) | Atributo multivaluado → tabla separada en U1·S3 |
| ¿Qué clientes no son contactables? | Regla: cliente debe tener al menos un contacto válido | Validación de negocio (S1) y verificación vía SELECT (S4) |

## **Tabla de contrastes**

| Términos | Definición operativa | Prueba rápida |
| :---- | :---- | :---- |
| **Dato** vs **Información** | El dato se convierte en información cuando tiene contexto y propósito. | ¿Quién lo usará y para qué? |
| **Información** vs **Conocimiento** | El conocimiento surge de patrones sobre múltiples informaciones. | ¿Describe un patrón o un caso único? |
| **Dato** vs **Metadato** | El metadato describe al dato (tipo, formato, restricciones). | ¿Es contenido de cliente o regla sobre el contenido? |

## **⚠ Atención (errores frecuentes)**

* Recolectar datos “por si acaso”: aumenta complejidad y no agrega valor.  
* Confundir *dato* con *metadato*: mezclar reglas de validación dentro del contenido.  
* Saltar a SQL sin definir las **preguntas de negocio** prioritarias.

## **✔ ¿Qué me llevo?**

* □ Lista de **preguntas de negocio** priorizadas para la U1.  
* □ Datos mínimos necesarios para responderlas (sin sobredimensionar).  
* □ Regla: cada cliente debe tener al menos un medio de contacto válido.  
* □ Reconozco la diferencia entre *dato, información, conocimiento* y *decisión*.
